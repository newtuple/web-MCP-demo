01 What WebMCP is

WebMCP is a browser API that lets a website hand its own JavaScript functions to an AI agent.

Instead of the agent looking at a screenshot of your page and guessing where to click, your page gives it a list like this:

add_to_cart      needs: productId (string), quantity (number)
apply_coupon     needs: code (string)
get_cart_total   needs: nothing

The agent picks one, fills in the values, and the browser runs your real function.

The API lives at document.modelContext. It is a W3C proposal from the Web Machine Learning Community Group, with Google and Microsoft driving it. Chrome ships it behind an origin trial.

02 The problem it solves

Today an agent uses a website the same way a person does, except worse.

It takes a screenshot. It guesses that the blue rectangle near the top is probably a search box. It clicks at pixel coordinates. It takes another screenshot to see what happened. Then it repeats.

WebMCP removes the guessing. Your page states what it can do, in words, with a schema. The agent reads that and calls the function directly.

03 How it works

Three parties. The agent never touches your page directly. Every interaction goes through the browser.

Read that as:

  1. Your page loads and calls registerTool() once per tool.
  2. The browser writes each one into a registry attached to that tab. It stores a pointer to your function, not a copy.
  3. The agent asks the browser for the list with getTools(). It gets names, descriptions and schemas. It does not get your functions.
  4. The agent picks one and calls executeTool(tool, args).
  5. The browser looks up the stored function and calls it with those arguments.
  6. Your function runs like normal app code. The screen updates because it is the app's real code doing the work.
  7. Your function returns a result. The browser passes it back to the agent.

04 Requirements

For your site

RequirementWhy
HTTPSThe API is marked SecureContext in the spec. It does not exist on plain HTTP. http://localhost is treated as secure, so local dev works.
No document.domainA document that opted into the legacy document.domain setter loses origin isolation and cannot use WebMCP.
Permissions Policy allows toolsDefaults to self, so your own page works out of the box. To allow an embedded iframe, send Permissions-Policy: tools=(self "https://partner.example").
No build step or libraryIt is a plain browser API. Vanilla JS is fine.

For testing locally

Enable the flag, then relaunch Chrome:

chrome://flags/#enable-webmcp-testing

For production

Join the WebMCP origin trial (available from Chrome 149) and add the token to your page:

<meta http-equiv="origin-trial" content="YOUR_TOKEN_HERE">

Feature detection

Always check before using it. Older browsers do not have it, and the API surface is still moving.

if ("modelContext" in document) {
  registerAllTools();
} else {
  console.info("WebMCP not available, site works normally");
}
Rule

Your site must work fine without it. WebMCP is an addition, never a dependency.

05 Making your first tool

Here is the smallest useful tool.

const controller = new AbortController();

await document.modelContext.registerTool({
  name: "add_todo",
  description: "Add a new item to the user's todo list",

  inputSchema: {
    type: "object",
    properties: {
      text: {
        type: "string",
        description: "The text content of the todo item"
      }
    },
    required: ["text"]
  },

  async execute({ text }) {
    addTodoToList(text);          // your existing app function

    return {
      content: [
        { type: "text", text: `Added todo: "${text}"` }
      ]
    };
  }
}, { signal: controller.signal });

That is the whole pattern. Five things:

  1. A name the agent will refer to
  2. A description in plain English
  3. An inputSchema saying what arguments it takes
  4. An execute function that does the work
  5. A signal so you can remove the tool later

The important part: execute should call the function your own UI already calls. Do not write a separate code path for the agent. If your Add button calls addTodoToList(text), your tool calls addTodoToList(text). One code path, one set of bugs.

06 The tool object in detail

Full shape from the spec:

dictionary ModelContextTool {
  required DOMString name;
  USVString title;
  required DOMString description;
  object inputSchema;
  required ToolExecuteCallback execute;
  ToolAnnotations annotations;
};

name

Required. What the agent calls it. Use snake_case. Use a verb. Be specific.

name: "add_itinerary_activity"    // good
name: "search_products"           // good
name: "handleClick"               // bad, means nothing to an agent
name: "doStuff"                   // bad

title

Optional. A human friendly label for UI that lists tools. "Add Activity" where name is add_itinerary_activity.

description

Required, and it matters more than people expect. This is the only thing the agent reads to decide whether to use your tool. Write it for someone who has never seen your app.

// bad
description: "Adds an activity"

// good
description: "Add an activity to an empty hourly slot in the itinerary. \
Fails if the slot is already occupied or if the traveler has manually \
edited that slot."

Say what it does. Say when it fails. Say what it will not touch.

inputSchema

Standard JSON Schema. This is a contract, and the browser validates against it, so use it properly.

inputSchema: {
  type: "object",
  properties: {
    date: {
      type: "string",
      description: "Local date in YYYY-MM-DD format"
    },
    hour: {
      type: "integer",
      minimum: 7,
      maximum: 22,
      description: "Start hour on a 24 hour clock"
    },
    category: {
      type: "string",
      enum: ["eat", "explore", "culture", "coffee", "rest"]
    },
    duration: {
      type: "number",
      minimum: 0.5,
      maximum: 8,
      description: "Length in hours"
    }
  },
  required: ["date", "hour"],
  additionalProperties: false
}

Things worth doing every time:

  • Put a description on each property, not just on the tool
  • Use enum for fixed choices, so the agent cannot invent a category
  • Use minimum and maximum on numbers
  • Say what format a string needs, because "date" alone means nothing
  • Set additionalProperties: false so typos get rejected instead of silently ignored

Every constraint you add is one fewer thing the agent can get wrong.

execute

Required. An async function. Gets the validated arguments as its first parameter.

async execute({ date, hour }, options) {
  // options.signal is an AbortSignal, for long running work
  const result = await myApp.addActivity(date, hour);

  return {
    content: [
      { type: "text", text: `Added at ${hour}:00 on ${date}` }
    ]
  };
}

The return shape is { content: [ { type: "text", text: "..." } ] }. Make the text useful. The agent reads this to decide what to do next.

// bad, tells the agent nothing
return { content: [{ type: "text", text: "OK" }] };

// good, agent knows the state now
return { content: [{ type: "text", text:
  `Added "Morning walk" at 9:00 on 2026-09-18. Day 1 now has 6 activities. \
Remaining empty slots: 7:00, 12:00, 17:00.` }] };

Failures should return a clear message rather than throwing:

async execute({ date, hour, title }) {
  if (slotIsTaken(date, hour)) {
    return { content: [{ type: "text", text:
      `Cannot add. ${hour}:00 on ${date} already has "${getSlot(date, hour).title}". \
Use update_activity to change it, or pick an empty hour.` }] };
  }
  // ...
}

That message tells the agent exactly how to recover. A thrown error just tells it something broke.

The second parameter carries options.signal, an AbortSignal. Pass it to fetch so a cancelled tool call actually stops the network request.

annotations

Optional hints about the tool's behaviour.

annotations: {
  readOnlyHint: true,           // does not change anything
  untrustedContentHint: false   // output may contain user or third party text
}

Set readOnlyHint: true on anything that only reads. Agents and browsers can use it to skip confirmation prompts on safe calls.

Set untrustedContentHint: true when your tool returns text you did not write, for example user comments or scraped content. It warns the agent that the text might contain instructions trying to hijack it.

Both are hints

Nothing is enforced. Do your own permission checks inside execute.

07 Removing tools

There is no unregisterTool(). You remove a tool by aborting the signal you passed at registration.

const controller = new AbortController();

await document.modelContext.registerTool(myTool, { signal: controller.signal });

// later
controller.abort();   // tool is gone from the registry

This is the most useful part of the API and the part most people skip.

Only register what is actually possible right now. If a tool cannot succeed in the current state, take it off the list. The agent then cannot even attempt it.

let checkoutController = null;

function onCartChanged(cart) {
  if (cart.items.length > 0 && !checkoutController) {
    checkoutController = new AbortController();
    document.modelContext.registerTool(checkoutTool,
      { signal: checkoutController.signal });
  }

  if (cart.items.length === 0 && checkoutController) {
    checkoutController.abort();
    checkoutController = null;
  }
}

Now checkout simply does not exist while the cart is empty. You did not have to write a check inside the tool, and the agent did not have to be told not to try.

Other cases where you should unregister:

  • Admin tools when the user is not an admin
  • submit_form while the form is invalid
  • Page specific tools when the user navigates away in a single page app
  • respond_to_comment when there are no comments

Group related tools under one controller if they share a lifetime:

const loggedInTools = new AbortController();

for (const tool of [profileTool, ordersTool, logoutTool]) {
  await document.modelContext.registerTool(tool, { signal: loggedInTools.signal });
}

function onLogout() {
  loggedInTools.abort();   // all three gone at once
}

08 Telling the agent the menu changed

The agent will not poll getTools() in a loop. The browser fires an event when the registry changes.

document.modelContext.ontoolchange = () => {
  // a tool was registered or aborted, re-read the list
};

You do not fire this yourself. The browser does it when you register or abort. It is on the agent side to listen. Worth knowing because it is why dynamic registration works at all.

09 The declarative HTML version

If your tool is just a form, you can skip JavaScript entirely.

<form toolname="search_cars"
      tooldescription="Search available cars by make and model"
      toolautosubmit>

  <input type="text"
         name="make"
         toolparamdescription="The vehicle's make, for example BMW or Ford"
         required>

  <input type="text"
         name="model"
         toolparamdescription="The vehicle's model, for example 330i or F-150"
         required>

  <button type="submit">Search</button>
</form>

Four attributes:

AttributeGoes onMeans
toolname<form>same as ModelContextTool.name
tooldescription<form>same as .description
toolautosubmit<form>boolean, lets the agent submit without a human click
toolparamdescriptionform controlsdescribes one parameter

The schema is derived from your inputs. name becomes the property name, required becomes a required field, type="number" becomes a number.

Use this for search forms, filters and simple lookups. Use the JavaScript API when you need enums, ranges, conditional logic, or a return value richer than a page navigation.

Careful

Leave toolautosubmit off for anything that spends money, sends a message, or deletes something. Without it the agent fills the form and stops, and a person presses the button.

10 Reading and calling tools

This is the agent side. You need it if you are writing your own agent, a test harness, or a browser extension.

// 1. get the list
const tools = await document.modelContext.getTools();

Each entry is a RegisteredTool:

{
  name: "add_todo",
  title: "Add Todo",
  description: "Add a new item to the user's todo list",
  inputSchema: { /* ... */ },
  window: Window,                          // which tab or frame owns it
  origin: "https://example.com",           // which origin registered it
  annotations: { readOnlyHint: false, untrustedContentHint: false }
}

Note there is no execute on it. The agent gets the menu, never the function.

// 2. call one
const tool = tools.find(t => t.name === "add_todo");

const raw = await document.modelContext.executeTool(tool, {
  text: "Buy milk"
});

executeTool returns a string, not an object. The browser serializes the result across the boundary.

// 3. parse it
const result = JSON.parse(raw);
console.log(result.content[0].text);   // "Added todo: \"Buy milk\""

Cancellation works through the options argument:

const ac = new AbortController();
setTimeout(() => ac.abort(), 5000);

await document.modelContext.executeTool(tool, args, { signal: ac.signal });

Turning the list into OpenAI tool format:

const openaiTools = tools.map(t => ({
  type: "function",
  function: {
    name: t.name,
    description: t.description,
    parameters: t.inputSchema
  }
}));

Into Anthropic format:

const anthropicTools = tools.map(t => ({
  name: t.name,
  description: t.description,
  input_schema: t.inputSchema
}));

Both are near one to one, because inputSchema is already JSON Schema.

11 Connection and session

There is no connection

This is the part that confuses people coming from regular MCP.

No server. No socket. No HTTP request. No handshake. No API key. No port.

executeTool() is a function call inside one browser process. It is the same thing as clicking a button, except the agent triggered it instead of your finger.

Regular MCP serverWebMCP
Where tools runseparate process or remote machinethis browser tab
Transportstdio or HTTPnone, direct call
Setupinstall a server, configure a tokenopen the page
Authits own credentialsthe user's existing session
Lifetimeuntil you stop the serveruntil the tab closes
Who exposes itbackend teamfrontend team

12 Which agents can use your tools

ChatGPT desktop app

Native support, no setup. Requirements:

  • Latest version of the ChatGPT desktop app
  • Use the built in browser inside the app, not Chrome or Safari
  • Model must be GPT-5.6 Sol or GPT-5.6 Terra. Luna has WebMCP disabled
  • Settings, then Browser, then Permissions, then Enable site tools
  • Not available on Enterprise or Edu workspaces

Once the page is open, ask normally. Check the tools were found by clicking Site tools in the address bar, then Available site tools. Site tools, then Recently used shows the actual calls with arguments and return values, which is the best debugging view you get.

Codex

Same desktop app, same built in browser. Codex discovers and calls the tools the same way.

Chrome, on its own

Chrome implements the API from version 149 under an origin trial. Any agent running inside Chrome can use it. Google also ships a Model Context Tool Inspector extension that lists registered tools, lets you invoke them by hand, and validates your schemas. Use that while developing.

Claude

No native support today. The Claude Chrome extension drives pages with screenshots and DOM snapshots and has no WebMCP path. There is an open feature request.

A way around it:

  1. A bridge extension plus a local webmcp-server. The extension reads the page's registered tools, forwards them over a WebSocket, and the server exposes them to Claude Code over stdio as normal MCP tools. Community projects exist for this.
